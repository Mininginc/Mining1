# Spec 0.1: Multi-company readiness (M1 Platform)
Status: Approved (Andrei chose "multi-company ready now", 2026-11-27) · ADR 0006
Serves: User access (5), Cybersecurity (5), Privacy/data compliance (1); enables selling the software to other dismantlers

## Scope
- `platform.companies`: id, name, slug (unique), home_state (e.g. `CA`), active, timestamps.
- `platform.company_locations`: id, company_id, name, state, address. State rules hang off the location.
- `company_id` (not null, FK) on `platform.users`, `platform.audit_log`, `platform.outbox`. Email unique per company, not globally.
- Row-level security on every table with `company_id`: rows visible only when `company_id = current_setting('app.company_id')::uuid`. Tables use `FORCE ROW LEVEL SECURITY`; the API connects as a role that is not a superuser and does not bypass RLS.
- Every request runs inside a transaction that sets `app.company_id` from the signed-in user's token. Login looks up the user by company slug + email.
- Seed creates the first company (Andrei's) and its admin. A separate `platform_owner` capability (not a company role) can create companies; not exposed in the app yet.
- Migration moves existing rows into the first company.

## Acceptance criteria
1. Two companies with users of the same email can both sign in, each only to their own company.
2. A user of company A gets 404 (not 403) for company B's user IDs, and audit lists never include B's rows.
3. With RLS on, a raw query run as the app role without `app.company_id` set returns zero rows from every company table.
4. A new company table without RLS fails a schema test that checks every table with `company_id` has RLS forced.
5. All Phase 0 tests still pass, now running inside a company.
6. Every module spec from now on lists `company_id` on its tables.
